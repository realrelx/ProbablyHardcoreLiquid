# 滴管修复 · 为什么原版 1ml/5ml 滴管在残留系统下吸不进去

> 结论：原版滴管并没有「固定吸 1ml」的硬编码。它的吸/倒是按「滴管是否空」二分的：
> **空 → 吸（能吸多少吸多少）；非空 → 倒出**。残留系统让它永远非空，于是它永远只会倒。
> v0.8.2 的修复 = 残留照旧，但「只剩残渣」等效于空（交互层分叉），不是给滴管免残留。

## 一、滴管是怎么造出来的

`FoodItemDirectory.Dropper1ml()`（IL 实证）：

```
Directory<GameItem>.Empty()
  .SetName(LocHelper.GetLocalizedItem("item_1ml_dropper_name"))
  .SetSpriteAndShape("Items/water_container3", "1ml")
  identifier = "1ml_dropper"; unitValue = 120
WaterHelper.InitLiquidContainerItem(item, capacityInMl: 1, basePrice: 120,
    isFilterContainer: false, isGraduated: true, isDropper: true,
    isTransparent: false, sheetPage: 3)
AudioHelper.InitPlasticBottle(item)
```

5ml 版本同理：`identifier = "5ml_dropper"`、`unitValue = 10`、
`InitLiquidContainerItem(item, 5, 10, false, true, true, false, 3)`。

`InitLiquidContainerItem` 里与滴管有关的两件事：

1. `isDropper == true` → 打开 **`LIQUID_CONTAINER_DROPPER_TAG`**；
2. `LIQUID_CONTAINER_CAPACITY = capacityInMl × 1000`（内部单位 µl，所以 1ml 滴管 = 1000µl）；
3. 把所有交互挂到 `onThisTargetItemFunc`（`Action<GameItem, GameItem>`，参数 = (被使用的物品, 目标物品)）——
   用 `Delegate.Combine` **追加** `<>c__DisplayClass10_0::b__9`，也就是说外部只能再叠一层，不能只改 tag。

## 二、b__9 的三条分支（问题所在）

| 目标 | 滴管状态 | 行为 |
|---|---|---|
| 排水口 | — | `EmptyContainer(self)` + DumpWater 音效 |
| 水龙头 | — | 按 `RUSTWATER_TAP` / `GUTTERFLOW_TAP` 解锁情况 `AddWater(...)` |
| 液体容器 | 滴管**空** | `TransferLiquid(target, self)` → 吸入，音量 `DropperDraw()` |
| 液体容器 | 滴管**非空** | `TransferLiquid(self, target)` → 倒出，音量 `DropperDrop()` |

`TransferLiquid(源, 目标)` 的语义（IL 实证）：`amount = min(目标剩余容量, 源总量)`，
按成分比例 `SplitProportionally` 分配后逐个 `ModifyTag`。
所以「一次抽满滴管」在原版本来就成立——1ml 滴管一次抽 1000µl，靠的是目标（滴管）剩余容量。

## 三、残留系统为什么让它坏掉

`ResidueLogic.Apply` 会在每次倾倒后把源容器补回到「残留体积 R」：
出液容器最多只失去 `(总量 − R)`，剩下的 R 与整瓶同比例。
滴管容量 1ml、R 按「容量 × 残留比例」算，哪怕只有 0.5% 也有 5µl——

于是滴管倒完永远剩 5µl → `IsEmpty(self)` 永远为假 → **永远走「非空 → 倒出」分支** →
用户点另一个容器时，滴管只会往外倒，再也吸不进东西。这就是「有残留就吸不动」。

## 四、修复（v0.8.2：保留残留，只改「什么算空」）

v0.8.1 曾用「滴管豁免残留」绕过问题——那等于把滴管从残留玩法里摘出去，用户指出这是错的。
v0.8.2 撤销豁免，改为在**交互层**加一个分叉（`src/Mechanics/Residue/DropperFix.cs`）：

```csharp
[HarmonyPatch(typeof(WaterHelper), "InitLiquidContainerItem")]
static class DropperFixPatch { static void Postfix(object[] __args) { DropperFix.Install(__args[0] as GameItem); } }
```

`Install` 只对带 `LIQUID_CONTAINER_DROPPER_TAG` 的物品动作，把原版 `onThisTargetItemFunc`
取出来存进闭包，换成一个包装委托：

| 条件 | 处理 |
|---|---|
| 目标是液体容器，且 `GetTotalVolume(self) ≤ 残留量 + 余量` | 反向 `TransferLiquid(target, self)` 吸取 + `DropperDraw()` 音效 |
| 其它任何情况（还有实质液体、目标不是容器、目标是排水口/水龙头） | 原封不动调用原版委托 |

判定上限 `ResidueCeilingUl(capacityUl) = 该容器的残留量 R + max(20µl, R/2)`，R 与
`ResidueLogic` 用同一套参数（`PercentValue` / `MaxUlValue`），所以残渣量始终跟着设置走。

因此：

- **残留机制完整保留**：滴管照常留残渣，残渣照常参与成分混合、照常算纯度；
- 只是「只剩残渣」不再被当成「非空」，滴管能重新吸——这正是用户要的语义；
- 配置项 `dropper_smart_draw`（设置菜单 `dropper` 组，默认开）。关闭即退回原版二分，
  可用来对照复现「有残留就吸不动」。
- 目标容器为空时直接吃掉这次交互并打日志，避免把管内残渣倒进空容器污染它。

## 五、没有被改动的东西

- `ResidueLogic.Capture` 不再有任何滴管特判（旧的 `DropperExemptValue` 一行已删除），
  残留对所有容器一视同仁——这是 v0.8.1 的错误做法的回退点。
- 没有改 `LIQUID_CONTAINER_CAPACITY`、`DROPPER_TAG` 或任何原版常量。
- 喷壶的 `Rinsing` 短路逻辑不变：清洗期间 `CaptureArg` 依旧直接返回 null。
- 用 `ConditionalWeakTable` 防重复安装；物品被销毁时表项随之回收，不会泄漏。
